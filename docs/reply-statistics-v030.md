# v0.3.0 回复统计与决策回放

## 根因与实现边界

原先把一个回合是否发过文字当作回复量，Replyer 调用、拆分气泡、表情和平台消息混为一谈。公共发送函数用 None 同时表达 Hook 中止、冷却、失败和未确认；上层统一写“发送消息失败”。本版复用现有 `data/decision_replay.db` 的 events/turns/requests，不重放消息或调用模型，不建立另一套无法关联的计数系统。

采集位置：底层 LLMOrchestrator 的实际 Replyer Provider 尝试开始、现有 Replyer 校验返回、Planner reply 动作/独立 @ 动作、公共发送服务的计划/跳过和 Platform IO Broker 的每驱动尝试/回执。发送成功后的存库或 Hook 错误不推翻平台确认。

## 指标定义

| 指标 | 事件与定义 |
| --- | --- |
| 回复生成请求次数 | Replyer 主生成任务的实际 Provider 调用尝试开始；失败和重试逐次计数，排除 Planner、表达选择等模型任务。SDK 不暴露的内部重试无法额外推算。 |
| 回复生成成功次数 | 现有生成器返回校验成功且有可用正文的生成结果。与发送分开计数。 |
| 逻辑回复次数 | 面向会话的 reply 动作或独立发送动作开始；同一动作的多气泡、附件和重试不增加。独立生成但没有回复动作不增加。 |
| 成功回复数 | 至少一条用户可见消息得到平台确认的聊天逻辑回复；首次可见事件在确认事务中派生且永久去重。 |
| 部分成功逻辑回复数 | 窗口内新建逻辑回复的当前 partial_success 数量，是状态快照，不是新的发送增量。 |
| 文本气泡成功发送数 | 平台确认成功、实际含 TextComponent 的聊天消息。 |
| 表情成功发送数 | 平台确认成功、实际含 EmojiComponent 的聊天消息。图片本身不当作表情；选中、计划、冷却均不计成功。 |
| 平台消息成功发送数 | 平台/账号/会话/平台消息 ID 去重；可信平台确认也可提供明确的 delivery_id。包含系统消息，可单独筛选。 |
| 发送尝试/失败/跳过/未知 | Broker 每次实际调用驱动为一次尝试；明确拒绝为失败；冷却/Hook/无驱动等为跳过；超时或仅有传输成功而没有平台确认则为未知。 |

纯文本、独立表情、混合、其他是互斥的内容分类；混合消息可同时贡献文本和表情维度，但平台总量只计一次。系统消息排除生成、聊天逻辑回复和聊天文本/表情指标，纳入平台与尝试指标。平台确认不表示用户已读。

逻辑回复先记录所需气泡计划，动态可选表情归入同一个动作，动作关闭后才判断完成。终态有全部成功、部分成功、全部失败、全部跳过、仍待确认；可选表情被跳过不破坏已成功正文。还没有发送动作的独立生成单独显示。一次生成与动作通过 generation_group_id/真实 generation_request_id 关联，不假设一对一。

## 关联与幂等

- decision_id 复用 replay 的 logical_turn_id；保留原 cycle_id 与实际 request_id。
- Planner 的 reply_id 与该动作扩展执行共享同一个标识，优先路径和无 Planner 的独立动作在实际入口创建，不伪造 Planner 阶段。
- 气泡在计划时固定 outbound_message_id；发送重试复用它，每次驱动调用有独立 attempt_id。成功确认保存 platform_message_id。
- reply_stats 事件采用确定性语义 event_id；回复首次可见事件、平台确认和语义去重键与回放事件在同一 SQLite 事务写入。
- 对核心统计事件先在线程中持久化再执行生成/发送，避免阻塞 bot/WebUI 事件循环；普通回放仍使用已有有界队列。队列丢弃或写入失败会显示采集缺口，不能把这些数据声称为完整审计。
- replay_metadata、reply_event_keys 和 outbound_dispatches 是同库的兼容辅助表，分别保存生效时间、去重键和无正文的最小发送安全状态；数字仍全部从 events 投影，不从另一个累计计数器读取。
- 去重键和发送安全状态不随时间线清理删除。已确认或结果未知的稳定出站 ID 不重新提交。平台不提供幂等时，不把未知当作安全失败；独立 @ 未知表情不自动回退第二条文字。
- 可信迟到回执可经 OutboundTracker 或 `reconcile_receipt` 关联原消息。仅接受唯一的内部 ID 对应关系；跨会话有歧义时不猜测。纯传输成功无平台 ID 的旧链保留未知。

## 页面、接口与窗口

入口：Dashboard 的“决策回放 / Decision Replay”，路径 `/decision-replay`。统一统计区共享会话和时间输入，提供来源、会话类型、内容类型和系统筛选；面板、关联事件和 JSON 导出使用同一投影。门控等旧回合列表筛选明确只作用于回合列表。

- `GET /api/webui/decision-replay/statistics`
- `GET /api/webui/decision-replay/statistics/export`
- `GET /api/webui/decision-replay/{decision_id}?session_id=...` 包含本回合的回复统计和贡献事件。

所有端点沿用 WebUI 认证。时间窗口统一 `[start,end)`，传 Unix 秒，页面明确使用 Asia/Shanghai。生成、确认、失败和跳过按各自事件时间入窗；跨窗口迟到确认只在确认窗口增加发送数，不重新增加旧窗口的逻辑回复数。另列窗口内新建回复的当前状态，允许后续确认更新它，不能与窗口增量再相加。

统计只覆盖保留期内的新口径事件，不称为生命周期累计总量。旧 schema=1 回放不回填精确生成/气泡/回复关系。新口径生效时间随第一个 v2 事件保存。关闭 debug.decision_replay_enabled 后暂停采集，页面明确显示停用，不能宣称停用期间数据完整。

旧首页的 `total_replies` 实际是带引用关系的消息记录数，详细成本统计的是 reply 工具记录，Replyer 监控的是日志记录数。本版保留兼容字段和旧数值，页面、日志及导出明确标注旧口径；新指标以决策回放页同源事件聚合为准，不能混加。

## 历史对照与已知限制

2026-10-15 16:10:20—2026-10-16 03:36:00 的旧数据记录 86 次 Replyer 调用，其中独立 @ 72、Planner 14；其中私聊不能算群聊主动回复。旧的 116 条主程序发送记录与 118 条网关发送记录是不同观察层，不能相加；网关外部自动好友提示及私聊差额不能凭主程序观测补造为聊天回复。

旧数据缺少完整 reply_id/出站计划/平台确认身份，不能可靠还原逻辑回复数、所有气泡和附件数量、精确部分成功状态。历史数不是新版本验收目标。

宿主所有 Broker/SendService 发送均可采集；系统发送方需明确设置 `message_info.additional_config['system_message']=True`。仅在 NapCat 内部自动产生而没有进入宿主发送链的好友提示不在宿主平台总量中；只有外部提供可信且可关联的确认才能纳入。该边界在解释网关差额时必须保留。

## 应用

QQ-Agent 版本按现有约定在 README、CHANGELOG 与 Git 标签升级为 v0.3.0；上游 MaiBot 1.3.5 和 Dashboard 包 1.8.4 的独立版本不改写。配置模板版本升级至 8.14.77，新增回放开关和保留期已有字段；不编辑实际 bot_config.toml/model_config.toml，不增加 ConfigUpgradeHook。

需要重启加载 Python 代码，部署 Dashboard 构建；已有回放库原始事件保留，初始化时只增加辅助表，不转换旧口径。运行前建议备份 SQLite（包括运行中的 WAL，或用 SQLite backup）。本次验证全部使用确定性模型/发送结果，没有向真实 QQ 发消息。
