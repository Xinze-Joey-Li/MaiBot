## 已确认原因

DeepSeek 默认自动缓存重复前缀，而非任意相同片段。资料：https://api-docs.deepseek.com/zh-cn/guides/kv_cache/ 。冷请求、服务端缓存生命周期及持久化时机也可能影响命中，因此请求前缀稳定不保证每次命中。

1. 冲突请求在固定短规则后首先发送每次变化的新标签，再发送长历史标签块，限制了历史块的前缀复用；原 JSON 还包含大量结构空格。
2. 人物事实提取开头直接插入人名，随后是本轮发言和机器人回复，最后才是大段稳定证据校验规则；人物或发言变化都会打断可复用前缀。
3. 保存的聊天请求中，独立 @ Replyer 系统文本只出现一个版本；普通 Replyer 为两个版本，Planner 为三个版本。当前证据不支持“每次随机系统提示词”是主因。同一会话历史增加可复用前缀，但上下文裁切或重写历史早期内容会打断；回放中 Planner 有 34 次、普通 Replyer 有 11 次相邻请求首先在第 1 个历史项变化（零基索引 1），不是仅尾部追加。
4. 表达选择及校验等短任务全部零命中；不能据此判断缓存机制关闭，也不应通过填充无意义文本提高百分比。人物事实任务虽不长，但规则放到前缀有直接优化空间。

## 本次修改

- tag_conflict_service：请求数据先 old_tags 后 new_tag，压缩 JSON 结构空白；维持原缓存键算法，不失效已经付费获取的持久化响应。候选、请求预算、冲突证据及裁决校验保持不变。
- tag_extraction_service：前文与上次标签置于消息之前，压缩 JSON；不删来源发言、摘要或引用。
- tag_memory_recall：仅压缩参考 JSON，不删除字段、证据或限制召回数量。
- memory_flow_service：固定提取与证据规则前置，人名、本轮发言、机器人回复后置。此处是既有内联提示词，未修改各语言 prompt 模板。
- 回归测试验证语义证据不丢失、冲突历史在前、JSON 紧凑、不同人物共享同一规则前缀。原断言对空格的依赖改为 JSON 语义验证。

JSON 紧凑化减少实际传输字符，预期减少对应输入 Token；确切 Token 节省依赖供应商 tokenizer，未以字符减少冒充 Token 实测。前缀排序优化主要减少未缓存输入费用及潜在首 Token 延迟，不代表总输入 Token 自动下降。
