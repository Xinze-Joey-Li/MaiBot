# 门控等待后 Planner 仍运行：触发排查

对本次完整运行按同一会话关联最近一次门控决定与后续 Planner 启动，限定时间差 0—30 秒：发现 10 次“等待更多消息”后启动，9 次是第 2 轮，1 次是第 3 轮；这个检索范围内没有第 1 轮案例。不将该有限检索结论推广为任何情况下都无问题。

具体例子（北京时间）：21:04:30 门控放行并启动第 1 轮；21:04:33 Planner 调用 reply；21:04:35—46 完成文字及表情发送；21:04:50、53 新消息被门控判等待；21:04:53 原逻辑回合合并新消息并启动第 2 轮；21:04:55 Planner 决定静默。

原因：MessageTurnScheduler 的等待决定只是不 enqueue 新的外部消息回合，不取消运行中的推理循环。reasoning_engine 工具执行后以 tool_continue 继续内部轮次；下一轮由 _collect_pending_messages_before_next_round 合并新消息，不重新调用外部门控。中断重试也存在在同一活跃回合直接重试 Planner 的路径。本批所检索的 10 个案例均为后续轮次，不能归为独立 @ 第一次触发或主调度器无视 should_trigger。

影响：已经放行的回合可以读到后来被门控拦下的消息；门控不对每次内部 API 调用重新准入，也不保证每次 reply 前重新验额度。后续 Planner 可能回复，也可能仅确认静默。本例第 2 轮仅确认静默，仍产生一次模型请求。

这是现有连续工具与推理机制的边界，用户既有要求保留已启动回合的内部工具连续性。本次仅排查，不将门控粗暴插入每个工具后，不取消工具结果处理，不修改代码。若要优化成本，应独立区分必要工具结果续轮、纯 reply 后续轮及新消息开启新回合，再确定精确结束条件。

证据：logs/test-start-20261014-165738.stderr.log；src/maisaka/turn_trigger/scheduler.py 的 should_trigger 分支；src/maisaka/reasoning_engine.py 的工具续轮、内部消息合并及 run_loop。
